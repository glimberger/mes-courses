# Privacy and Security Checklist: Shopping Lists

**Purpose**: Check that the requirements for protecting the user's data, on the device and when it leaves it, and for keeping the builds, accounts and dependencies that ship the app trustworthy, are complete, clear, consistent and justified before implementation starts
**Created**: 2026-10-06
**Feature**: [spec.md](../spec.md) (FR-027, FR-030 to FR-030c, Assumptions, Success Criteria), with [research.md](../research.md) R4, R13, R18b, R23 and R24, [plan.md](../plan.md) and [tasks.md](../tasks.md) T013, T134, T139 and T140

**Note**: This custom checklist is generated by the `/speckit-checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

**Audience and depth**: reviewer, standard depth, used as a gate before `/speckit-implement`. The fields an error report keeps, the device name and the installation identifier are covered by [observability.md](observability.md) (CHK011 to CHK014, CHK031, CHK033); backups and encryption of the stored data by [data.md](data.md) (CHK030, CHK033); scanning for leaked credentials and release credentials by [delivery.md](delivery.md) (CHK015, CHK024, CHK025). They are not repeated here.

## Data on the Device

- [x] CHK004 - Is it specified that the app's stored data is reachable only by the app itself (the system sandbox), with no export, share or file access path in this feature? [Gap, Spec §FR-027]
- [x] CHK005 - Is the exposure of the data through system backups (held by Google or Apple, and readable on a restored phone) accepted explicitly, including who can restore it? [Assumption, Spec §Assumptions, Research §R18b]
- [x] CHK006 - Is it required that release builds write no list, article, category or quantity text to the device log, which other tools on a connected computer can read? [Gap, Spec §FR-030]
- [x] CHK007 - Is the way user text reaches storage required to keep it as data, never as part of a storage command (values given as parameters), so a name such as `'); DROP TABLE` is stored as typed? [Gap, Research §R4]
- [x] CHK008 - Are the reports queued on the device while offline (at most 30) covered by the same "no list content, no personal data" rule as sent reports, in the spec's own words? [Consistency, Spec §FR-030, Spec §FR-030a]

## Data Leaving the Device

- [x] CHK009 - Is it stated that error tracking is the only outbound connection the app makes in this feature, so any other network call is a defect? [Gap, Spec §FR-027, Spec §FR-030]
- [x] CHK010 - Does "a report MUST keep only" these fields cover attachments a tracking SDK can add on its own (screenshots, view hierarchy, logs), or are attachments named and excluded? [Clarity, Spec §FR-030, Research §R13]
- [x] CHK011 - Is the transport of reports required to be encrypted (HTTPS only), or is that left to the SDK's default without being written down? [Gap, Assumption, Research §R13]
- [x] CHK012 - Is the error tracking service's data region (EU or US) chosen and recorded, given the maintainer lives in France and reports can carry an installation identifier? [Gap, Compliance, Research §R13]
- [x] CHK013 - Is the retention period of reports at the error tracking service specified or explicitly left at the service's default? [Gap, Research §R13]
- [x] CHK014 - Is the fact that the reporting address (DSN) ships inside the app, where anyone can read it, accepted explicitly, along with what happens if someone sends fake reports to it? [Assumption, Research §R13]
