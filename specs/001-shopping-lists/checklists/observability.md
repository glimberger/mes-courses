# Observability and Error Tracking Checklist: Shopping Lists

**Purpose**: Check that the requirements for error tracking (constitution Principle VIII) are complete, clear, consistent and measurable before implementation starts: which errors are reported, what a report holds, how reporting behaves offline and when it fails, and how the result is checked
**Created**: 2026-10-06
**Feature**: [spec.md](../spec.md), with [contracts/driven-ports.md](../contracts/driven-ports.md) (`ErrorReporter`), [contracts/ui-screens.md](../contracts/ui-screens.md), [research.md](../research.md) R12a, R13, R18a and R18c, and [quickstart.md](../quickstart.md) §6

**Note**: This custom checklist is generated by the `/speckit-checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

**Audience and depth**: reviewer, standard depth, used as a gate before `/speckit-implement`. Already covered and not repeated here: storage error text stripped from reports ([data.md](data.md) CHK032), the fixed list of report fields, the meaning of "personal data" and the operation and screen of each scenario ([testability.md](testability.md) CHK030 to CHK032), and telling a full storage apart from other failures ([testability.md](testability.md) CHK029).

## Scope of Reported Errors

- [x] CHK001 - Does the spec define "unexpected error" by a rule or an exhaustive list of the expected situations that are not reported (full storage, data from a newer version, refused form input), so every other failure is known to be reported? [Clarity, Spec §FR-030, Spec §FR-040]
- [x] CHK002 - Are errors that no use case catches (uncaught exceptions, unhandled promise rejections) required to be reported in the spec, or does that rule live only in the constitution and research R13? [Gap, Traceability, Spec §FR-030, Research §R13]
- [x] CHK003 - Is it specified whether native crashes (outside JavaScript) are reported, and with which of FR-030's fields, given they have no operation or screen? [Gap, Coverage]
- [x] CHK004 - Is the behavior specified when a screen fails while drawing (an unexpected error outside a data load or a save): what the user sees, whether the app can continue, and that the error is reported? [Gap, Exception Flow, Spec §FR-029]
- [x] CHK005 - Is it stated which failed reads outside the four data screens (for example loading a category list in a dialog, or reading the current list after "Terminer les courses") are reported, and with which operation and screen? [Coverage, Spec §FR-029, Contract §ui-screens]
- [x] CHK006 - Is it stated that a failure inside an action whose outcome the user already sees as an error (for example a failed "Annuler") is still reported, consistent with "recovered from with an outcome the user can see, or reported"? [Consistency, Spec §FR-030, Contract §ui-screens]
- [x] CHK007 - Is it defined whether one failure caught by the UI adapter can also reach the global handlers, and that each failure gives exactly one report? [Gap, Ambiguity, Research §R13]

## Report Content

- [x] CHK008 - Are "error type" and "error code" defined for errors that are not storage errors (a JavaScript error with no code, a rejected promise holding a non-error value)? [Clarity, Spec §FR-030]
- [x] CHK009 - Is "stack trace" defined as the list of frames without the error's first line, given that a JavaScript stack string starts with the error's own text, which FR-030 removes? [Ambiguity, Spec §FR-030, Research §R13]
- [x] CHK010 - Is the stack trace required to be readable for the deployed build (symbolicated), as Principle VIII demands, or does FR-030 only require that one is present? [Gap, Spec §FR-030]
- [x] CHK011 - Is "application version" defined precisely enough to tell two builds apart (version name, build number, or both)? [Clarity, Spec §FR-030]
- [x] CHK012 - Is "device model" distinguished from the device's own name (often the owner's first name, such as "iPhone de Marie"), so the name is excluded as personal data? [Ambiguity, Spec §FR-030]
- [x] CHK013 - Does the spec say whether a report carries any user or installation identifier, and if it does, that it is pseudonymous as Principle VIII requires? [Gap, Assumption, Spec §FR-030]
- [x] CHK014 - Is the operation and screen of a report raised by the global handlers defined (absent, or a fixed value), since no use case names them? [Gap, Spec §FR-030, Contract §ErrorReporter]
- [x] CHK015 - Is "the screen it happened on" defined for an error raised after the user has left the screen where the action began (a save finishing after navigation, a failed "Annuler")? [Clarity, Spec §FR-030, Contract §ui-screens]
- [x] CHK016 - Is removing every breadcrumb (the user's recent steps) recorded as a deliberate choice, with what the maintainer gives up for diagnosis? [Assumption, Research §R13]

## Environments

- [x] CHK017 - Are the values of "environment" defined for every kind of build (store release, internal or preview build, development, end-to-end test build), and which of them send reports at all? [Clarity, Spec §FR-030, Research §R13]
- [x] CHK018 - Is it a requirement, not only a plan decision, that no automated test and no local development run sends data to the real tracking service? [Traceability, Plan §Constitution Check]
- [x] CHK019 - Is it specified what a build without tracking configured does with an error (printed to the console, with or without the error's text), and that this never applies to a store release? [Completeness, Research §R13, Quickstart §6]

## Offline and Reporting Failures

- [x] CHK020 - Does the spec require that a report raised offline is kept and sent when connectivity returns, as Principle VIII requires, or is that only in research R13? [Gap, Traceability, Spec §FR-030]
- [x] CHK021 - Is the bound of the offline queue stated, and which reports are kept when it is full (oldest dropped, newest dropped)? [Clarity, Research §R13]
- [x] CHK022 - Is it stated whether queued reports survive the application being stopped or the device restarted before connectivity returns? [Gap, Recovery]
- [x] CHK023 - Is "reporting never blocks the user and never breaks the application" stated as a requirement of this feature, so a test can cite it, rather than only in the `ErrorReporter` contract? [Traceability, Contract §ErrorReporter]
- [x] CHK024 - Is the startup case covered: an error raised before reporting is set up, or a failure of reporting setup itself, still shows the FR-039 error state? [Edge Case, Spec §FR-039, Research §R18a]

## Volume and Repetition

- [x] CHK025 - Is a limit or grouping defined for repeated reports of the same failure ("Réessayer" tapped many times, every tick failing on a broken storage), or is reporting each one again an explicit choice? [Gap, Spec §FR-029, Spec §FR-039]
- [x] CHK026 - Is it stated whether every error is sent or a sampled share, given the free-tier limits that research R13 relies on? [Gap, Assumption, Research §R13]

## Consistency Across Documents and Features

- [x] CHK027 - Do the spec, the constitution and research R13 agree on the bounded offline queue, symbolication, the pseudonymous identifier and non-blocking reporting, with each rule placed in one document and cited by the others? [Consistency, Spec §FR-030, Research §R13]
- [x] CHK028 - Do the reporting rules of 002 (FR-011) and 003 (FR-022, FR-022a) point to 001 FR-030 for report fields and privacy, rather than restating them in other words? [Consistency, Spec §FR-030]
- [x] CHK029 - Is the line between expected and unexpected situations drawn the same way in 001 (full storage not reported) and 003 (offline or unreachable server not reported, repeated sync failures reported)? [Consistency, Spec §FR-030]

## Verification of Observability Requirements
