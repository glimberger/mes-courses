# ADR-0014: Changelog generated with git-cliff in the release bump

- **Status**: Proposed
- **Date**: 2026-11-10
- **Decided by**: proposed by the agent, approved by the maintainer
- **Supersedes**: none
- **Related**: constitution Principles I, IV and VI;
  [014 research](../../specs/014-changelog-git-cliff/research.md) R1, R2, R8;
  [ADR-0009](0009-version-identity-from-git.md)

## Context

Releases had no changelog: the GitHub Release body was generated by GitHub from pull request
titles, CI and test noise included, and the app had nothing to show its users about a new
version. The history is a linear list of squash-merged Conventional Commits ending in `(#N)`
(ADR-0009), which is enough to build a changelog without writing one by hand. The app screens of
#203 and #204 need the same content as structured data, not only as markdown.

## Decision

We generate the changelog with [git-cliff](https://git-cliff.org), provided by the Nix dev shell
(`flake.nix`) and pinned by `flake.lock`, so the maintainer's machine and CI run the same version.
No npm package is added.

- `cliff.toml` at the root holds the filtering and grouping only: it keeps `feat`, `fix`, `perf`
  and breaking changes, and drops the noise types and scopes.
- `pnpm release` runs git-cliff once, with `--context`, for the commits since the last `vX.Y.Z`
  tag, behind a `ChangelogGenerator` port. A pure domain module turns that JSON into a section and
  renders both `CHANGELOG.md` and `apps/mobile/src/changelog/changelog.json` from it, so the two
  files carry the same data by construction.
- Both files are committed in the release-bump pull request. They are generated and never edited
  by hand: a wrong entry is fixed in `cliff.toml` (or the rendering) and regenerated.
- `changelog.json` is a stable contract for the app: an array of sections, newest first, each
  `{ version, date, features, fixes, performances, breaking }` with entries `{ text, pr }`.
- The `Release` workflow takes the GitHub Release body from the committed `CHANGELOG.md`, so it
  does not need git-cliff.

## Consequences

- A release brings its changelog with no manual step; the Release body and the app show the same
  entries.
- The quality of the changelog depends on commit subjects: a vague subject gives a vague entry.
- git-cliff is one more tool in the dev shell; its `--context` JSON is an interface the adapter
  depends on, covered by a test against a fixture repository with the real binary.
- A change to the `changelog.json` shape is a change for the app screens that read it.

## Alternatives considered

- **GitHub generated notes**: keep the noise, give no data file for the app.
- **Two git-cliff templates (markdown and JSON)**: two outputs can drift, and JSON escaping in a
  template is fragile.
- **A hand-written parser of the history**: re-implements what git-cliff already does (Conventional
  Commits, scopes, breaking changes), with more code to test (Principle IV).
- **A hand-maintained `CHANGELOG.md`**: forgotten or inconsistent; nothing for the app to read.
